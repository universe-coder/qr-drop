# QR Drop

[English](README.md) · [Русский](README.ru.md) · [中文](README.zh.md) · **العربية** · [Français](README.fr.md)

**انقل ملفًا من جهاز إلى آخر عبر سلسلة من رموز QR.** تعرض شاشة تسلسلًا لا ينتهي من الرموز، ويصوّره الجهاز الآخر ويعيد تجميع الملف. بلا خادم ولا شبكة ولا اقتران: شاشة وعدسة فقط.

**التطبيق مباشرة:** https://universe-coder.github.io/qr-drop/

## لماذا يعمل دون قناة راجعة

لا يستطيع المستقبل أن يطلب إعادة إطار: لا وسيلة لديه ليقول ذلك. وفي الوقت نفسه تفوّت الكاميرا نصف ما يُعرض أو أكثر. الكتل المرقّمة المعروضة في حلقة لا تصلح هنا: مع فرق ثابت بين معدل تحديث الشاشة ومعدل الكاميرا، قد تفوت الأرقام نفسها إلى الأبد.

لذلك يستخدم QR Drop **الترميز النافوري (LT)**: كل إطار هو XOR لمجموعة عشوائية من الكتل الأصلية، ويكفي المستقبل أي `K·(1+ε)` إطارًا، أيًّا كانت. يستنتج الطرفان مجموعة الكتل في الإطار من رقمه وحده، فلا يمر عبر القناة أي بايت لوصف الكتل.

| المرحلة | الإطارات | المحتوى |
|---|---|---|
| منهجية | `seq mod 5K < K` | كتلة أصلية واحدة بالضبط |
| نافورية | الباقي | XOR وفق توزيع سوليتون متين مع سُلّم للبقايا |

تمنح المقدمة المنهجية الحالة المثالية: **مع استقبال نظيف يُجمَّع الملف في K إطارًا بالضبط**، دون أي تكلفة إضافية. وتتكرر المقدمة كل `5K` إطار لمن وجّه الكاميرا متأخرًا.

### التكلفة الإضافية المقيسة

عدد إطارات البيانات لكل كتلة أصلية، محاكاة مفكك BP، 60 تشغيلًا لكل نقطة:

| K | فقد 0% | 30% | 50% | 60% | 75% |
|---|---|---|---|---|---|
| 137 | 1.00 | 1.23 | 1.28 | 1.33 | 1.39 |
| 1024 | 1.00 | 1.21 | 1.19 | 1.21 | 1.30 |

## صيغة الإطار

ترتيب little-endian. خمسة بايتات مشتركة: التوقيع `QD`، والإصدار مع النوع، ومعرّف الجلسة.

**DATA**: ‏13 بايت تكلفة إضافية ثم الحمولة.

</div>

```
0  'Q' 'D'                    2
2  (version << 4) | type      1
3  session                    2
5  frame number               4
9  payload                    blockSize
.. CRC-32C                    4
```

<div dir="rtl">

**META**: ‏59 بايت إضافة إلى الاسم ونوع MIME: حجم الملف، وحجم الكتلة، وعدد الكتل، وSHA-256 للملف، وبصمة الجدول، والاسم، ونوع MIME.

مواضع إطارات الوصف هي `0, 4, 8 … 28`، ثم واحد كل 16 موضعًا. من يوجّه الكاميرا من البداية يحصل على وصف الملف باحتمال يقارب 98% خلال أول 32 موضعًا حتى مع فقد 60%؛ وفي الحالة المستقرة لا تشغل إطارات الوصف إلا 1/16 من التدفق.

- **CRC-32C وليس CRC-16.** يمزج المفكك النافوري الإطار في عدة كتل دفعة واحدة، فإطار تالف واحد لم يُكتشف يفسد الملف كله بصمت، ولن يُعرف ذلك إلا من SHA-256 بعد دقائق.
- **بصمة الجدول في META.** يشغّل الطرفان الشيفرة نفسها، لكن قد تعمل إحدى علامات التبويب على نسخة قديمة مخزّنة. تحوّل البصمة «بيانات عشوائية بعد ثلاث دقائق» إلى خطأ صريح منذ البداية.
- **وضع البايتات الخام في QR، دون base45/base64.** تُرجع jsQR قيمة `binaryData` دقيقة؛ تم التحقق على 700 بايت تتضمن أصفارًا وبايتات أكبر من `0x7F`.

## أوضاع النقل

| الوضع | إصدار QR | التصحيح | الوحدات | بايت/إطار | إطار/ث | ‏100 ك.ب فعليًا |
|---|---|---|---|---|---|---|
| موثوق | 13 | M | 69×69 | 316 | 8 | ~95 ث (1.1 ك.ب/ث) |
| عادي | 19 | L | 93×93 | 776 | 10 | ~38 ث (2.7 ك.ب/ث) |
| سريع | 25 | L | 117×117 | 1260 | 12 | ~25 ث (4.0 ك.ب/ث) |

كلما زادت البيانات في الإطار صغرت الوحدات وارتفعت متطلبات الكاميرا والإضاءة وثبات اليدين. يفترض التقدير «الفعلي» أن الكاميرا تقرأ 35–55% من الإطارات المعروضة، مع احتساب تكلفة الترميز النافوري. الحد الأقصى لحجم الملف 2 م.ب: وهذا وحده نحو ساعة ونصف من التصوير.

## البنية

```

  protocol/     pure core without DOM, fully testable
    crc32.ts        CRC-32C
    prng.ts         splitmix32 + distinct index sampling
    soliton.ts      robust soliton distribution
    schedule.ts     ★ the one place where encoder and decoder must agree
    frames.ts       frame serialization
    encoder.ts      file → endless frame stream
    decoder.ts      incremental LT peeling decoder
    receiver.ts     receive session: META, foreign sessions, integrity
  qr/
    capacity.ts     capacity table, block size selection
    encode.ts       bytes → module matrix
    paint.ts        matrix → canvas
    broadcast.worker.ts  frame generation off the main thread
    scan.worker.ts       recognition and parsing off the main thread
  platform/       camera, wake lock, saving, vibration
  app/            hooks and state
  ui/             screens, i18n, small component kit
    locales/        one dictionary per language, all typed against ru.ts
```

<div dir="rtl">

- **الإرسال.** تُولَّد الإطارات في Worker، مع 12 إطارًا جاهزًا مسبقًا. يتبع العرض عدّادًا لنبضات `requestAnimationFrame` لا الساعة: يجب أن يبقى كل إطار عددًا صحيحًا من تحديثات الشاشة، وإلا سيقع التبديل عاجلًا أو آجلًا في منتصف تحديث، فتلتقط الكاميرا نصف الإطار القديم ونصف الجديد.
- **الاستقبال.** لا يُقرأ إلا المربع المركزي تحت إطار التصويب، مصغّرًا إلى 512×512: أرخص بثلاث مرات، ويتجاهل في الوقت نفسه رموز QR الغريبة عند الحواف. ولا تُطلب اللقطة التالية قبل الانتهاء من تحليل السابقة.

## التطوير

</div>

```bash
npm install
npm run dev       # http://localhost:5173
npm run check     # types + lint + tests
npm run build     # static site in dist/
```

<div dir="rtl">

لا تعمل الكاميرا إلا عبر HTTPS أو على `localhost`. لاختبار الاستقبال على الهاتف، قدّم نسخة التطوير عبر HTTPS (مثلًا عبر نفق) أو استخدم الموقع المنشور.

يشغّل `npm run check` مجموعة الاختبارات، ومنها: نقل في حلقة مغلقة مع فقد 20/50/70% من الإطارات، واستقبال يبدأ من منتصف التدفق، ورحلة ذهاب وإياب ثنائية عبر رموز QR حقيقية مرسومة بكسلات ومقروءة من جديد بـ jsQR، والتحقق من أن إتلاف أي بايت في الإطار يكشفه CRC.

## النشر

الموقع ثابت بالكامل ويستخدم مسارات نسبية، لذا يمكن تقديم `dist/` من أي استضافة وأي مسار فرعي.

إعداد GitHub Pages موجود في [`.github/workflows/pages.yml`](.github/workflows/pages.yml): كل دفع إلى `main` يشغّل الفحوصات ويبني الموقع وينشره. إعداد لمرة واحدة: **Settings → Pages → Build and deployment → Source: GitHub Actions**.

## مفاضلات معروفة

- **jsQR بدلًا من zxing-wasm.** zxing-wasm أسرع بنحو الضعف، لكنه يعتمد على ملف WASM يُحمَّل افتراضيًا من CDN. لتطبيق جوهره العمل دون اتصال، هذه مقايضة خاسرة.
- **لا يرى المرسل تقدّم المستقبل.** القناة باتجاه واحد، وادعاء غير ذلك ليس أمينًا. تعرض شاشة الإرسال مدتها ورقم الدورة، وتطلب صراحة متابعة التقدم على الجهاز الآخر.
- **لا يُستخدم `BarcodeDetector` الأصلي.** فهو لا يُرجع إلا `rawValue`، أي نصًا وليس بايتات.
